## 1. Problem

Milestone 1 proved the exact-beat domain model and two read-only views, but the
prototype has no real audio source or calibrated relationship between musical
beats and media time. A user therefore cannot yet begin the intended workflow
with an MP3 or WAV recording.

Milestone 2 must deliver one reviewable vertical slice in which a user imports
audio, establishes a constant-tempo beat grid, plays and seeks the recording,
and sees the waveform, beat grid, counts, and playhead agree in both views.
Musical beat positions remain authoritative; seconds are derived from the BPM
and anchor.

## 2. Scope

### 2.1 In scope

- Lightweight new-project setup for importing one MP3 or WAV file and
  calibrating its grid.
- Manual BPM entry and spacebar tap-tempo estimation.
- One primary anchor at any musical `one` and one optional later calibration
  point for refining a single global BPM.
- Play, pause, stop, seek, duration, errors, and one shared playhead.
- A basic non-editable waveform in the Timeline.
- Beat/count labels in Timeline and Sheet, including count origin, local and
  optional continuous numbering, per-region group sizes, partial groups, and
  configurable restart behavior.
- CAD-style wheel zoom, middle-button pan, and toolbar zoom controls required
  for inspecting the waveform and grids.
- Automated domain, decoding, presentation, and GUI tests plus actual review
  screenshots.

### 2.2 Out of scope

- Musical-region creation or editing, simple sequence generation, and
  Structure mode; these belong to Milestone 3.
- Choreography editing, selection, snapping, conflict handling, and undo/redo;
  these belong to Milestone 4. Calibration APIs must nevertheless be usable by
  a future command layer.
- Project save/load, audio embedding, migration, recovery, or recent files.
- Region looping. S-020 makes it conditional, and this milestone has no
  structure-selection workflow with which to define a loop.
- Playback speed changes, pitch shifting, metronome, count-in, transient or
  beat detection, audio trimming, recording, and audio export.
- Multiple songs, multiple anchors, multiple calibration points, variable or
  piecewise tempo, and automatic drift correction.
- Production packaging or non-Linux release validation.

## 3. Binding product behavior

### S-M2-01 — Imported audio and transactional setup

Accept local files with `.mp3` or `.wav` extensions only. Successful import
must also be confirmed by the decoder; an extension alone is not evidence of a
valid file. Record display name, resolved local source, duration, and decoded
format metadata in an audio/session layer separated from the pure domain.

The setup sequence is:

1. Select an MP3 or WAV file.
2. Confirm that metadata and decoding can be opened.
3. Enter or tap an initial BPM.
4. Seek to a musical `one` and set the primary anchor.
5. Optionally add a calibration point.
6. Enter the editor.

Canceling setup, canceling the file chooser, or encountering an unreadable,
empty, unsupported, or falsely named file leaves the prior project/session
unchanged and shows an actionable error. The optional structure step from
S-066 is deferred to Milestone 3 rather than represented by a nonfunctional
control.

### S-M2-02 — Exact constant-tempo calibration

Introduce a GUI-independent calibration value with:

- positive BPM stored as an exact `Fraction` parsed from decimal user input;
- an exact anchor beat and exact anchor media time in seconds;
- optionally, one calibration beat and its media time.

The selected primary musical `one` becomes beat `0` for a new project. The
grid extends to negative beats before it. This convention does not force count
labels to begin there: count origin remains separate and editable.

Conversions use:

```text
seconds(beat) = anchor_seconds + (beat - anchor_beat) * 60 / BPM
beat(seconds) = anchor_beat + (seconds - anchor_seconds) * BPM / 60
```

The optional calibration point is placed by selecting a continuous grid beat
and the matching audio position. Its beat and media-time deltas from the anchor
must have the same nonzero sign. Recalculate the one global BPM as:

```text
BPM = 60 * beat_delta / seconds_delta
```

Moving the anchor or changing/refining BPM never rewrites region or move beat
positions. It only changes their derived media times. Invalid or degenerate
calibration input is rejected without mutating the last valid calibration.

### S-M2-03 — Manual and tapped BPM

Manual BPM accepts a positive decimal value and parses it exactly; the UI may
limit displayed precision but must not store a binary float as authoritative
calibration data.

Tap tempo is active only while its setup control has focus. Ignore keyboard
auto-repeat. Two taps produce the first estimate; every later tap recomputes:

```text
BPM = 60 * (tap_count - 1) / (last_tap_seconds - first_tap_seconds)
```

This makes a longer tapping interval improve precision as requested in S-004.
Three seconds without a tap starts a new session. Provide an explicit reset.
Spacebar taps must not simultaneously toggle playback. Accepting the estimate
feeds the same calibration state and validation path as manual entry.

### S-M2-04 — Audio playback and shared position

Use one playback controller for the application. It owns media state and
exposes source, duration, position, playing/paused/stopped state, volume, and
errors without exposing Qt objects to the domain layer.

- Play starts or resumes the imported source.
- Pause retains position.
- Stop returns position to the start of the media.
- Seeking clamps to `[0, duration]`.
- Loading a different source stops the old source and commits only after the
  replacement is known to be readable.
- End of media leaves the controller stopped at the media end until an
  explicit seek or play restarts it.

Timeline and Sheet observe the same controller position. Both show a playhead
or current-beat cue. Switching views preserves playback state and brings the
current position into view without mutating the project.

### S-M2-05 — Waveform

Decode MP3 and WAV through Qt Multimedia and reduce decoded PCM to deterministic
min/max peak buckets. Mix channels for display only; do not rewrite audio.
Waveform extraction runs without blocking the GUI, reports decode failure, and
caches peaks in memory for the current source. It need not persist a cache.

Render the waveform in the continuous Timeline behind or adjacent to the beat
grid. Show the anchor, optional calibration point, and shared playhead above
the waveform. Waveform and beat geometry use the same seconds-to-pixel mapping,
so zooming and seeking cannot make them drift visually.

### S-M2-06 — Counts

Preserve exact beats as the underlying coordinate system. Extend count
presentation so that:

- local dance counts are primary;
- continuous beat numbers can be toggled as a secondary reference;
- count origin is independently configurable and may differ from the anchor;
- beats before the origin use ending pickup counts from the preceding group;
- the project has a positive default group size;
- a region may override group size;
- incomplete final groups are valid and retain their true duration;
- every region defaults to restarting at `1`, but can instead continue the
  preceding sequence; and
- changing count notation never changes beat timing, audio, regions, or moves.

Both views must consume the same GUI-independent count mapping. Existing M1
fixture behavior must be migrated without losing exact timing.

### S-M2-07 — Zoom and navigation

For both Timeline and Sheet:

- mouse wheel zooms around the pointer;
- middle-button drag pans;
- toolbar actions zoom in, zoom out, and zoom to fit; and
- each view retains its own zoom level.

Zoom and pan change presentation state only. They do not alter project data or
playback position. Timeline waveform, grid, regions, moves, and playhead must
share one transform.

## 4. Implementation constraints

### I-M2-01 — Preserve architecture

Keep `domain`, audio/file I/O, presentation mapping, and Qt widgets separate.
Domain tests must run without importing PySide6. Do not add persistence or a
general command framework to make calibration work.

### I-M2-02 — Audio backend

Use PySide6 Qt Multimedia:

- `QMediaPlayer` plus `QAudioOutput` for playback;
- `QAudioDecoder` for waveform PCM; and
- `QMediaFormat`/actual decoder results for capability and failure reporting.

Do not add a second media runtime unless this backend fails an MP3/WAV
acceptance fixture on the Linux target. If it fails, stop and report the tested
file, backend diagnostics, and candidate fallback rather than silently adding
FFmpeg subprocesses or another decoder library.

A pre-handoff spike on the current environment decoded a synthetic MP3 through
Qt Multimedia's FFmpeg backend successfully. Qt's format-capability query did
not list MP3 even though actual decoding succeeded, which is why real decode
results—not only advertised formats—are binding for import validation.

### I-M2-03 — Test media

Commit very small, programmatically generated, license-safe WAV and MP3
fixtures. Document their origin. Tests must not depend on a user's music,
network access, microphone, or a system `ffmpeg` executable.

Use fake clocks for tap-tempo tests and adapter fakes for deterministic
playback-state tests. Keep a small real-backend decode/smoke layer for both
required formats. Audio-output hardware absence must not invalidate domain or
decoder tests; report any manual audible-playback limitation explicitly.

### I-M2-04 — Incremental delivery

Implement in this order:

1. Calibration/count-domain values and tests.
2. Audio import probe and test fixtures.
3. Playback controller and shared session position.
4. Waveform extraction and presentation data.
5. Timeline/Sheet playback and count integration.
6. Guided setup and zoom/navigation controls.
7. Automated evidence, actual screenshots, and manual audible-playback review.

Each completed issue must update `docs/progress_tracker.csv` with code anchors
and evidence. Preserve M1 regression coverage.
