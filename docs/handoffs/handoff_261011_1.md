## 1. General description / context

Koreo is a Linux-first desktop application for planning dance choreography against a beat-based musical structure. Its eventual V1 workflow imports audio, calibrates musical beats, defines sections and count groups, edits choreography moves, and produces a readable sheet with PDF and Excel exports. **This handoff implements only the first foundation milestone**, not that full workflow.

The product separates (1) musical regions and their hierarchy, (2) choreography tracks and moves with independent song-relative timing, and (3) alternative visual representations. Musical beat positions are authoritative; audio seconds are derived later from BPM and an anchor. The product targets common dance-song structures, not formal score notation or advanced meters.

**Milestone 1 objective:** Deliver a tested, GUI-independent Python domain model and a runnable **read-only** PySide6 prototype showing the **same representative project** in a continuous Timeline view and a wrapped Sheet view, with a functioning view switch. Provide screenshots and an explicit human review checkpoint. Prioritize architectural correctness and legibility over visual polish.

## 3. Specifications

### S-M1-01 — Pure Python domain layer

Provide an importable Python package containing domain entities and validation, with **no dependency on PySide6** or GUI event objects. Keep the public model small, typed, and documented.

Minimum entities:

1. **Project**: stable ID; ordered track references; musical regions; moves; song-level count-group default and count origin or equivalent notation metadata. An audio object is not required.
2. **MusicalRegion**: stable unique ID, arbitrary label, exact absolute start beat, exact positive duration, optional parent ID; hierarchical nesting must be representable without a fixed depth.
3. **ChoreographyTrack**: stable unique ID, editable-in-future name, display order and color metadata.
4. **Move**: stable unique ID, track ID, exact absolute start beat, exact positive duration, short label, optional detailed notes.

An implementation may use immutable value objects or validated mutable objects; choose one consistent approach. Keep domain identity separate from labels. Avoid duplicating a move under musical sections.

### S-M1-02 — Exact musical coordinates

Use `fractions.Fraction` or an equivalent exact rational representation for **stored** beat positions and durations. Allow integer and fractional beat positions; positive durations are mandatory. Beat positions may precede the display count origin if needed for pickup material. Document whether the API uses zero-based beat coordinates and keep that convention consistent across model, fixture, and renderer. Pixel coordinates may be floating-point.

Use **half-open intervals** `[start, end)` for interval comparisons in this milestone; adjacent intervals sharing a boundary are not overlaps. This is a technical convention, not a user-visible counting rule.

### S-M1-03 — Domain validation

The domain layer must detect and reject invalid project states, at minimum:

- Duplicate IDs within each entity type, unknown track references, missing parent references, cycles in region hierarchy.
- Non-positive durations and non-rational/invalid timing values at the domain boundary.
- Overlapping sibling musical regions; gaps between siblings are valid.
- Children extending outside their parent's interval.
- Overlapping moves assigned to the same track; gaps allowed, moves on separate tracks may overlap.

Validation must be callable without the GUI, produce useful diagnostics, and not silently repair data. It is acceptable for this milestone to construct valid projects and validate them explicitly rather than implementing the future command/transaction framework. Do not implement conflict-resolution UX.

### S-M1-04 — Read-only Timeline view

Render the representative project on a **continuous horizontal beat axis**. Show beat/count reference marks, labeled musical regions (with understandable nesting or hierarchy cues), track headers, and move rectangles aligned to their beat intervals. Distinguish tracks visually. The same beat position must align across musical regions and moves. A simple scrollable viewport is sufficient; sophisticated zoom/pan is not required yet.

No audio waveform is expected. No drag handles, editing affordances, or deceptive clickable controls. The viewport must be usable on a typical Linux desktop without content being clipped beyond recovery.

### S-M1-05 — Read-only wrapped Sheet view

Render the **same project instance** as a wrapped, count-oriented grid with visible section labels, count groups, track rows, and labeled moves. Use a simple deterministic line-wrapping rule (for example, a fixed configurable number of beats per line) for the prototype; this does **not** freeze V1's eventual automatic layout algorithm. Counts and move timing must remain aligned across tracks.

If a move crosses a wrap boundary, render it as segments with a visible continuation cue while preserving its single logical identity in the model. Display an unassigned musical gap distinctly from a move-free count cell. Long labels should remain understandable (wrapping or accessible full text); the final print typography is out of scope.

### S-M1-06 — View switching and shared data

Provide a visible Timeline / Sheet toggle or tabs. Switching views must not mutate the project and both views must derive their content from **one shared project instance**, not duplicate fixture-specific data models. The prototype may use one default display context; Structure/Choreography editing modes are not required for this milestone. Include a window title or simple project identification.

### S-M1-07 — Representative deterministic fixture

Provide a reusable in-code or local test-data fixture, **not a native saved project file**, with:

- At least three named musical sections including repeated labels and a visible unassigned gap.
- At least one parent region with nested subdivisions.
- At least two choreography tracks with distinct labels/colors.
- Several moves, including moves on different tracks overlapping in time, a move crossing a musical section boundary, and a move crossing a Sheet wrap boundary.
- A fractional-beat position and at least one partial count group or non-eight-count grouping.

All fixture data must pass domain validation. Keep fixture values centralized so both views and tests use the same source.

### S-M1-08 — Architectural boundaries

Use clear separation between `domain`, `presentation/view-model or mapping`, and `gui` responsibilities. GUI rendering converts exact beats to display coordinates; it must not own domain invariants or timing. Avoid speculative plugin systems, generalized event buses, and over-engineered abstractions. Future commands, audio, persistence and exporters should be possible without replacing the model, but **do not implement them now**.

## 5. Tests (T-…)

Use pytest for automated domain tests. GUI smoke tests may use pytest-qt if available or an equivalent lightweight approach; avoid brittle pixel-perfect assertions.

| ID | Test / evidence | Pass condition |
|---|---|---|
| T-01 | Exact timing | Integer and fractional beat coordinates survive arithmetic without floating-point drift. |
| T-02 | Region hierarchy | Valid nested regions pass; missing parent, cycles and out-of-parent children fail with clear diagnostics. |
| T-03 | Region siblings | Adjacent and gapped siblings pass; overlapping siblings fail. |
| T-04 | Move tracks | Same-track adjacent/gapped moves pass; same-track overlaps fail; different-track overlaps pass. |
| T-05 | Identity and fields | Duplicate IDs, unknown track IDs and non-positive durations fail; repeated display labels are allowed. |
| T-06 | Fixture integrity | Shared fixture validates and includes every case required by S-M1-07. |
| T-07 | Sheet segmentation | A crossing move produces multiple display segments tied to the **same** move ID, with unchanged total beat interval. |
| T-08 | Shared presentation | Timeline and Sheet map the same source move IDs, region IDs and beat intervals. Switching views does not mutate project data. |
| T-09 | GUI smoke | Application starts on the target Linux environment; both views render without exception; toggle works. |
| T-10 | Human visual review | Deliver actual screenshots for both views and a runnable prototype; human approval is **pending** until explicitly given. |

Tests should be runnable from documented commands. If a GUI test cannot run headlessly in the execution environment, report the limitation and provide a reproducible manual smoke-test procedure; do not claim it passed.
